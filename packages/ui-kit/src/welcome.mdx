# @kubermatic/ui-kit

Shared React component primitives and design tokens for Kubermatic dashboards.

**32 primitives** — button, dialog, table, form controls, sidebar and the rest —
built on [Base UI](https://base-ui.com) and Tailwind CSS 4, plus the OKLch
light/dark token set they render against.

This Storybook is the workbench for that kit: every primitive is exercised here
against **both** token sets, and every story doubles as a browser test.

---

## Requirements

React 19 and Tailwind CSS 4. Angular applications (`dashboard-v2`) cannot
consume this package.

## Install

The package is published to GitHub Packages, so a consuming repository needs an
`.npmrc` line pointing the scope at that registry:

```
@kubermatic:registry=https://npm.pkg.github.com
```

Then:

```bash
npm install @kubermatic/ui-kit
```

## Wiring it up

Two steps. Both are load-bearing — skipping either produces an application that
builds successfully and then renders unstyled.

### 1. CSS

```css
@import 'tailwindcss';
@import 'tw-animate-css';
@import 'shadcn/tailwind.css';

/* Tailwind ignores node_modules when scanning for classes. Without this the
   kit's utilities are purged: in kubevirt-manager the stylesheet dropped from
   118 KB to 51 KB and the components rendered unstyled. */
@source '../node_modules/@kubermatic/ui-kit/dist';

@import '@kubermatic/ui-kit/theme.css';
```

Adjust the `@source` path so it resolves from the CSS file's own location.

Re-brand by redefining any custom property _after_ the `theme.css` import —
there is no need to fork the components. See **Foundations → Design Tokens**
for the full catalogue of what can be overridden.

### 2. Import

```tsx
import { Button, Badge, Table } from '@kubermatic/ui-kit';
```

The build emits one module per component with `preserveModules`, so unused
primitives tree-shake away.

## Dependencies

Only the packages that carry React context or hook identity are **peers**. A
second copy of one of those silently breaks context across the package
boundary — a form that cannot see its own provider, or an invalid-hook-call.

`react` · `react-dom` · `react-hook-form` · `tailwindcss`

Everything else the kit needs, it owns and installs itself, and consuming apps
get it transitively:

`@base-ui/react` · `lucide-react` · `class-variance-authority` · `clsx` ·
`tailwind-merge`

## How to read this Storybook

| Section         | What is in it                                                          |
| --------------- | ---------------------------------------------------------------------- |
| **Foundations** | The design token set — colour, radius and layout scales, read live     |
| **Primitives**  | One entry per component, each with a `Playground` and a variant matrix |

A few conventions worth knowing before you browse:

- **The theme toolbar is the point.** Every story is written to be reviewed in
  both light and dark. The toggle sets a `.dark` class on the wrapper _and_ on
  `documentElement`, which is the same mechanism consuming applications use —
  so portalled content (dialogs, dropdowns, tooltips) follows it too.
- **`Playground` is always the first story** and is driven by the controls
  panel. `Variants` renders the complete matrix in one frame; that is the story
  a token change gets reviewed against.
- **Overlays render open.** Dialogs, sheets, popovers and menus have an
  open-by-default story, because a closed trigger screenshots nothing.
- **Stories are tests.** They run in Playwright Chromium through
  `@storybook/addon-vitest`. Some carry a `play` function that asserts a
  computed value rather than mere presence — `Primitives/Button → CssCheck`
  asserts that `bg-primary` actually resolved to its token, which is what
  catches a broken Tailwind `@source` scan.
- **Accessibility is enforced, not advisory.** axe runs over every story at
  `test: 'error'`, so a missing button name, an unlabelled input or a colour
  pair below WCAG AA fails the build. Because story-level a11y only runs against
  the default theme, **Foundations → Contrast** measures every token pair in
  _both_ themes and asserts none of them fail.

## Local development against a consuming application

```bash
npm install file:../ui-kit
```

A linked checkout resolves the kit's _own_ `node_modules` copies of React and
friends, which produces `Cannot read properties of null (reading 'useContext')`
at runtime. Dedupe in both `vite.config.ts` and `vitest.config.ts`:

```ts
resolve: {
  dedupe: ['react', 'react-dom', 'react-hook-form'],
}
```

Keep that list in sync with `peerDependencies`. It is harmless once the package
is installed from the registry, where npm hoists a single copy.

## Known constraints

- **`min-release-age`** — `kubermatic-virtualization` pins `min-release-age=7`
  in its `.npmrc` as supply-chain hardening, so a freshly published version is
  refused for seven days. Plan releases ahead of that repository's needs, or
  have it waive the setting for the `@kubermatic` scope.
- **`kubelb-dashboard` has diverged.** It carries its own copies of 19 of these
  primitives, and `button`, `badge`, `dialog`, `card` and `table` differ on
  essentially every line. The token names already agree, so reconciliation is
  tractable — but it is a design decision, not a mechanical merge.
- **`kdp-dashboard` is Next 16.** Components are unmarked client components, so
  consuming them from a server component needs a `"use client"` boundary.

## Contributing a story

Conventions for writing and reviewing stories — the title taxonomy, the four
story skeletons, token discipline and the design-review checklist — live in
`.agents/skills/maintain-ui-kit-storybook/`. Coding agents load it
automatically; it reads as plain documentation otherwise.

The short version:

```bash
npm run storybook   # workbench on :6006
npm run typecheck   # stories are type-checked too
npm test            # unit tests + every story as a browser test
npm run lint:fix    # ESLint autofix, then Prettier
```
